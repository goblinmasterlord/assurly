## Design decisions worth the next reader's time

**The ceiling measures from `auth_time`, not `iat`.** `iat` moves on every renewal, so a cap
measured from it would cap nothing — it would slide along with the window it is supposed to
bound. `auth_time` is the original magic-link login and is copied forward untouched. Named
after the OIDC claim with the same meaning rather than inventing one.

**12 hours, not 8.** The ceiling exists to bound a stolen token, and between 8 and 12 that
difference is marginal **next to the fact that there is no revocation at all** — that is the
real exposure, and REQ-013 is where it gets fixed. What is not marginal is the user: at 8
hours, a 08:30 sign-in ends at 16:30, **mid-afternoon and mid-task**, and re-entry costs an
email round trip on a possibly different device. **12 makes "sign in once a day" true for every
working pattern in a school.** One environment variable if the posture changes.

**Old tokens fall back to their own `iat`.** Tokens minted before this change carry no
`auth_time`. Refusing them would have signed **everyone** out at deploy — a self-inflicted
instance of the defect being fixed. Falling back to `iat` caps them from issue, at most one
token lifetime old.

**`renewal_allowed(None)` returns `False`, not `True`.** Refuse rather than grant an uncapped
session. The fallback above means no real token reaches that branch, but the default should be
the safe one if a malformed token ever does.

**`_to_epoch_seconds()` exists because `datetime.timestamp()` is wrong here.** python-jose
encodes `exp` and `iat` treating a **naive datetime as UTC**; `datetime.timestamp()` treats one
as **local time**. Using it would have shifted `auth_time` by the host's offset and made the
ceiling wrong by that amount on any non-UTC host. Cloud Run runs UTC, so this would have been
invisible in production and wrong everywhere else — verified against `calendar.timegm`, which
is what jose itself calls.

**The renewed `user` block is read from the database, not copied from the presented token**, so
a user whose school or MAT changed since login renews into their current context.

## What was deliberately not changed

- **`RefreshTokenRequest` (`auth_models.py:17`) and `TokenPayload.type == "refresh"`.**
  **Reported as asked: they belong to option B and should stay unused.** `RefreshTokenRequest`
  expects a `refresh_token` in a request body; §3a takes **no body** and renews the token in the
  `Authorization` header, so adopting the model would misdescribe the flow in the OpenAPI spec.
  Option A mints **only** access tokens, so nothing should ever set `type` to `"refresh"`.
  **Left in place rather than deleted** — a correct placeholder for what REQ-013 may pick up,
  and deleting it would only have to be undone.
- **`get_current_user`'s bare `except Exception`** (`main.py:536`). It converts its own `401`
  into a `500` and is now recorded in REQ-013's scope. Fixing it here would have changed
  authentication behaviour on **every** endpoint inside a gate scoped to session renewal.
- **`datetime.fromtimestamp` on `exp` and `iat` in `verify_token`.** Local-time reads of
  UTC-encoded claims — see Findings. Not touched: they are pre-existing, invisible on a UTC
  host, and unrelated to the ceiling, which uses its own UTC-correct path.

## Findings — flagged, not fixed

- **`verify_token` reads `exp` and `iat` with `datetime.fromtimestamp`, which is local time**,
  while they are written as UTC. On a non-UTC host `TokenPayload.exp` and `.iat` are wrong by
  the offset. **Nothing currently depends on those two fields** — expiry itself is enforced by
  `jose` inside `jwt.decode`, not by these values — so this is latent, not live. **The new
  `auth_time` path deliberately does not share it.** Worth correcting when something first
  needs to read `exp`; correcting it now would be an unrelated change inside an auth gate.
- **`POST /api/auth/refresh` costs a database round trip**, because `get_current_user` queries
  `users` on every authenticated request. That is the existing pattern and the endpoint should
  not be special-cased — but if the frontend renews aggressively (say every minute rather than
  near expiry), it is a query per client per minute. **The contract tells clients to renew when
  remaining life falls below a threshold**, which keeps it to roughly one call per hour.
- **Both `401`s from §3a mean the same thing to the user.** They are worded differently for the
  log. **A client that branches on the wording will break** when it changes; the contract says
  so explicitly.

## Verification

- **Compiles and boots under the pinned stack:** 46 routes (was 45), **42 operations / 30 paths**
  (was 41/29) — exactly one endpoint added, nothing displaced. OpenAPI 3.1.0; `/api/auth/refresh`
  present and carrying `HTTPBearer`.
- **Behaviour exercised through the HTTP layer**, with `get_current_user` overridden, not by
  reading the code:

  | Case | Result |
  |---|---|
  | Valid token inside the ceiling | `200`, `expires_in` 3600, `auth_time` preserved |
  | Valid token past 12h | `401` "Session has reached its maximum length of 12 hours" |
  | **Expired token** | `401` "Invalid or expired token" — **renews, does not resurrect** |
  | Renew at 11h59 | `200`, and **the child token is not renewable two minutes later** |
  | Legacy token with no `auth_time` | verifies, falls back to `iat`, renewable |

- **The sliding property was checked directly, not inferred:** a token renewed from a 5-hour-old
  `auth_time` has a window of exactly 60 minutes **from now**, while `auth_time` stays 5 hours
  old. The window slides; the ceiling does not.
- **`_to_epoch_seconds` checked against `calendar.timegm`** on three dates, including the epoch.
  Match on all three. **My first assertion of this used a hand-computed epoch constant that was
  itself wrong** — the helper was right and the test was wrong, which is exactly the shape §2.2's
  preamble warns about, so it was re-run against the library's own convention rather than a
  number I had typed.
- **Route ordering checked, not assumed** — no parameterised sibling exists under `/api/auth/`,
  so nothing can shadow the literal. Three defects of that class have originated in this file.
- **Not verified:** anything in production. No database access (§2.4). **The live
  `JWT_ACCESS_TOKEN_EXPIRE_MINUTES` is reported as 60 in Cloud Run** and the code now derives
  `expires_in` from it either way.
