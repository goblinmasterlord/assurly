## What was deliberately not changed

- **`main.py:2497`**, the bare `aspect_code = %s` remaining in the file. It is the `SET` clause
  of the archive-rename in `delete_aspect` — **an assignment, not a comparison.** Wrapping it
  in `UPPER()` would silently uppercase codes on deletion.
- **The stored data.** Nothing was normalised; the endpoints were made tolerant instead. That
  is the right order — normalising first would have fixed HLT and left the next tenant's
  seeded data to rediscover the same bug.
- **`mat_standards`.** `standard_code` may have the same problem. Noted as out of scope for
  REQ-040's first pass rather than investigated here.

## Root cause

**`aspect_code` has no canonical casing, and nothing enforces one.** `POST /api/aspects`
uppercases on write (`:2178`), so every code created through the API is uppercase — which is
exactly why the assumption looked safe to whoever wrote the comparisons. The lowercase codes
(`ab`, `ey`, `mck`) are **seeded data that predates or bypassed that path**, the same two-era
seeding that produced the UUID versus `{MAT}-{CODE}` split in primary keys.

**The endpoints assumed an invariant the write path enforces and the data does not.** That is
now three defects of one shape in this table, which is what REQ-040 exists to stop.

## Findings — flagged, not fixed

- **`POST /api/assessments` failed loudly and misleadingly, which is worse than the silent
  case the requirement was written around.** `404 "No standards found for aspect: X"` for an
  aspect that has standards. **A silent empty list invites a second look. A confident error
  message about missing standards sends the reader to the wrong table** — and it blocked
  assessment creation outright for three of HLT's aspects. Worth generalising: when triaging a
  class of defect by symptom, the loud instances are not automatically the ones already
  understood.
- **`GET /api/assessments/by-aspect` had two comparison sites in one handler.** Finding one and
  stopping would have left the endpoint half-fixed and apparently working — the first site
  gates the CROSS JOIN that builds the shell, the second gates the standards query that fills
  it. **A grep that counted endpoints rather than sites would have missed it.**
- **`standard_code` on `mat_standards` is the obvious next candidate** and was not checked.
  Same table family, same seeding history, same uppercase-on-write assumption in
  `POST /api/standards`. Out of scope here; named in REQ-040 as the follow-on pass.
- **`aspect_category` and `standard_type` are enums with fixed lowercase values** and are
  compared exactly in several places. Not checked either — but they are DB-level enums, so the
  database constrains them in a way `aspect_code` is not constrained. Lower risk, worth one
  look during REQ-040.
