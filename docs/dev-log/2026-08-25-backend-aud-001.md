## The five questions

### 1. Does a terms table exist, and does it carry start and end dates?

**Yes, and yes.** `terms` (data model §7) is real, populated and dated:

| Column | Type | Null |
|---|---|---|
| `unique_term_id` | `varchar(20)` PK | NOT NULL |
| `term_id` | `varchar(10)` — `T1`/`T2`/`T3`, not unique | NOT NULL |
| `term_name` | `varchar(50)` | NOT NULL |
| `start_date` | `date` | **NOT NULL** |
| `end_date` | `date` | **NOT NULL** |
| `academic_year` | `varchar(10)` | NOT NULL |

It is described as "fully static reference data", currently holding three terms each for
2023-24 through 2026-27. `assessments.unique_term_id` and `standard_evidence.unique_term_id`
are both FK-constrained to it with `RESTRICT` on delete.

**So the dates exist.** The problem is not their absence — it is that almost nothing reads
them. See question 4.

### 2. Is there any concept of term state — open, closed, current?

**No state. "Current" exists, but it is computed two different and mutually inconsistent
ways.**

There is no `status`, `state`, `is_open` or `closed_at` column on `terms`, and no table
carrying term state. A repository-wide search for term-close concepts returns nothing in
either the backend or the frontend. **REQ-015 is therefore introducing term state for the
first time, not adding a close action to an existing model** — which is exactly the
possibility the plan flags at line 367, now confirmed.

"Current term" is derived, and the two derivations disagree:

| Where | How | Basis |
|---|---|---|
| `GET /api/terms` — `is_current` field (`main.py:2561`) | `CURDATE() BETWEEN start_date AND end_date` | **Calendar** |
| `GET /api/dashboard/schools` — `current_term` field (`main.py:1315-1330`) | Most recent term that *has assessment rows* for the selected view, ordered `academic_year DESC`, then `T3 > T2 > T1` | **Data** |

These are not the same thing and will disagree routinely. Today's date (25 August 2026)
falls in no term at all — it is the summer vacation between the 2025-26 and 2026-27 academic
years — so `is_current` is currently `false` for **every** row in `terms`, while the
dashboard's `current_term` happily returns the most recent term carrying data. The two
fields share a name and mean different things.

The frontend consumes the calendar one with a silent fallback:
`AssessmentInvitationSheet.tsx:266` and `:356` both do
`terms.find(t => t.is_current) || terms[0]`. During any vacation period, that `||` is the
branch that fires, and the default term becomes whatever sorts first — not a deliberate
choice.

### 3. What computes "overdue", and what does it compare against?

**The frontend, alone, against a per-assessment `due_date` — never against term dates.**

`assurly-frontend/src/utils/assessment.ts:14`:

```ts
export function isOverdue(item: { status: AssessmentStatus; due_date: string | null }): boolean {
    if (!item.due_date) return false;
    if (item.status === 'completed' || item.status === 'approved') return false;
    return new Date() > new Date(item.due_date);
}
```

Three consequences that bear directly on REQ-009:

- **`due_date` is nullable and optional.** It is set only at assessment creation, from the
  invitation sheet's date picker, which permits no date at all
  (`AssessmentInvitationSheet.tsx:331` — `dueDate ? format(...) : undefined`). Where it is
  null, `isOverdue` returns `false` unconditionally. **An assessment with no due date can
  never be overdue, however old it is.** Nothing backfills a due date from the term's
  `end_date`.
- **"Overdue" does not exist server-side.** The `status` filter on `GET /api/assessments`
  (`main.py:876-880`) filters the *derived group status*, whose `CASE` expression can only
  ever produce `not_started`, `completed` or `in_progress` (`main.py:838-843`). There is no
  `overdue` branch. `?status=overdue` returns an empty set. The frontend compensates by
  filtering client-side (`Assessments.tsx:329`).
- **The group's due date is `MAX(a.due_date)`** across all standards in the school × aspect ×
  term group (`main.py:838`, documented at contract line 848). A group is therefore overdue
  only once the *latest* standard in it is overdue — an aspect containing one badly overdue
  standard and one due next month reads as not overdue.

**Nothing anywhere compares against `terms.end_date` to determine overdue.**

### 4. Does anything else validate against term dates?

**No. Term dates are read in exactly one place in the entire codebase.**

`grep` for `start_date|end_date` across `assurly-backend/*.py` returns two lines, both inside
the single `GET /api/terms` query (`main.py:2560-2561`). The frontend references them only as
type declarations (`types/assessment.ts:273-274`) and the `is_current` flag.

Concretely, this means:

- No write path checks whether a term is current, past or future. An assessment for
  `T1-2023-24` can be created and rated today, three years after that term ended, and
  nothing objects.
- No validation that an assessment's `due_date` falls within its own term's date range.
- No mechanism turns the calendar over. `notify_on_term_open` exists as a column
  (`user_aspect_assignments`, data model §14) and as a Pydantic field (`main.py:353, 364`),
  but **there is no term-open event, no scheduler and no notification code**. The table is
  empty in production. The feature is declared, not built.
- There are no `.sql` migration files anywhere in the repository, consistent with plan §2.4
  (migrations written and applied manually).

**The load-bearing conclusion for M3:** term dates today are decorative. They render a label
and set one boolean. Gating editability on term state means building the state, the
transition and the enforcement from scratch — the dates give M3 a starting value, nothing
more.

### 5. Is there an existing per-school scoping structure applicability could attach to?

**No. M5 introduces the school ↔ standard relationship for the first time.**

`mat_standards` is MAT-scoped with no school dimension. `assessments` is the only table
carrying both `school_id` and `mat_standard_id`, and it is the *result* of an assessment
existing, not a statement about whether a standard applies.

The one existing per-school scoping structure is `user_aspect_assignments` (§14), which
joins `user_id` × `mat_aspect_id` × nullable `school_id`. Three reasons it is the wrong
attachment point:

- It scopes **responsibility**, not applicability — who gets notified, not what counts.
- It is at **aspect** granularity; applicability per REQ-018 is per standard.
- It is **empty in production**, and its documented uniqueness invariant
  `(user_id, mat_aspect_id, school_id)` is noted as "not currently enforced".

**Warning for M5 scoping:** absence of an assessment row cannot be used as an applicability
signal. It already conflates "this standard does not apply to this school" with "nobody has
created this assessment yet" — and the second is common, since assessments are created in
batches from the invitation sheet. Any applicability model needs its own explicit
representation.

## What was deliberately not changed

Everything. Per the AUD-001 brief this task is read-only: no term scheduling capability, no
date columns, no change to how the current term is determined. All defects below are
recorded for triage in M3, M5 or their own requirement, and none were acted on.

## Root cause

Not a defect session. But the shape of the gap is worth stating plainly: the term model was
built as **reference data** — a labelling vocabulary for grouping assessments — and three
separate pieces of downstream work now want to treat it as a **state machine**. The dates
were carried along from the start and never wired to anything. That is a different and
cheaper problem than a missing model, and it should be scoped as "add state and enforcement
to an existing dated table", not as "build a term model".

## Assumptions made

- **`terms` row counts and contents are taken from the data model document (§7,
  "Current data: 2023-24 … 2026-27"), not verified against the live database.** This session
  had no database access. If terms for 2026-27 were never populated, question 2's finding
  about `is_current` being false everywhere is worse than described, not better.
- **`assessments.due_date` population rates are inferred from the write paths, not measured.**
  Every creation path I traced makes it optional. I could not measure how many of the 1000
  production rows actually carry one. **This number decides how bad the REQ-009 overdue
  behaviour is in practice and should be checked before REQ-009 is scoped** — a single
  `SELECT COUNT(*) FROM assessments WHERE due_date IS NULL` settles it.

## Findings — flagged, not fixed

- **Two conflicting definitions of "current term" sharing a name** (question 2). The
  dashboard's `current_term` is not the calendar-current term and cannot be, since it is
  sourced from whichever term has data. Recommend renaming one of them; `current_term` in
  the dashboard response is more honestly `selected_term` or `latest_term_with_data`. This is
  a contract-visible field name, so it is a contract change, not a code change.
- **Every term is `is_current: false` for roughly a third of the year.** The vacation gaps
  between terms are not covered by any row's date range. Today is in one. The frontend's
  `|| terms[0]` fallback masks it rather than handling it.
- **`GET /api/assessments?status=overdue` silently returns an empty set** rather than an
  error, because `overdue` is not a value the grouped `CASE` can produce. A caller cannot
  distinguish "no overdue assessments" from "this filter does not work". Directly relevant to
  **REQ-009**.
- **Group due date is `MAX(due_date)`, which hides overdue standards behind later-dated
  siblings in the same aspect.** Also directly relevant to REQ-009 — this looks like a
  contributing cause of the "filter operates at the wrong level" symptom, and REQ-009's audit
  should start here rather than in the frontend filter code.
- **`GET /api/assessments`'s `term_id` filter matches on `SUBSTRING(unique_term_id, 1, 2)`**
  (`main.py:865`), i.e. on `T1`/`T2`/`T3` only. Passing `term_id=T1` without also passing
  `academic_year` returns T1 across *every* academic year. Whether that is intended is not
  obvious from the contract; §"Get assessments" documents the param but not the cross-year
  behaviour.
- **`notify_on_term_open` and `notify_on_due_date` are declared but unimplemented.** Columns
  and Pydantic fields exist; no notification code does. If REQ-015's term close is expected
  to notify anyone, that is net-new work, not wiring.
- **`user_aspect_assignments` has an unenforced uniqueness invariant** (§14). Empty today, so
  cheap to add a constraint before it fills. Relevant to M2, which will touch responsibility
  modelling.

## Correction — back-dated creation is intended behaviour

Question 4 above notes that "an assessment for `T1-2023-24` can be created and rated today,
three years after that term ended, and nothing objects." That is accurate but the framing
implied a defect. **It is not.** Creating an assessment against a past term is desired and
must remain available by default. **Term close is the only gate** — until a superadmin closes
a term, it stays open for both creation and editing. The finding stands; the behaviour it
describes is correct. Recorded in the plan at REQ-015 (v2.5).

## Correction — "current term" is deferred, not open

Confirmed as a real defect, and deliberately **not** fixed in M1. It resolves in M3: once
term state exists, current term becomes "the most recent open term" derived from state, and
**both** existing derivations are deleted. Recorded as an M3 design input on REQ-015 (v2.5).

## Follow-up 1 — `GET /api/terms` sort order

**Checked. The frontend fallback has *not* been selecting an arbitrary term — but it selects
the wrong end of the range.**

The backend orders **mixed-direction** (`main.py:2570`):

```sql
ORDER BY academic_year DESC, FIELD(term_id, 'T1', 'T2', 'T3')
```

Academic year descending (newest first), then term *ascending* within the year. Raw API
order therefore puts **T1 of the newest academic year** at index 0 — the oldest term of the
newest year.

The saving grace is that the only consumer re-sorts. `AssessmentInvitationSheet.tsx:245-260`
rebuilds the list as fully descending (year DESC, then term number DESC) and calls
`setTerms(sortedTerms)`, so both `sortedTerms[0]` at line 266 and `terms[0]` at line 356 are
reading a correctly sorted list. This is the only consumer of `getTerms()` in the
application.

**But the selected term is still wrong during the gap.** With `terms` populated through
2026-27, a fully-descending sort puts **T3 2026-27 — Summer Term 2027 — at index 0**. Through
the current August vacation, when `is_current` is false for every row, the fallback therefore
defaults the invitation sheet to a term roughly a year in the *future*, not the term that
just ended. Deterministic, not arbitrary, and arguably worse than arbitrary because it looks
deliberate.

Two flags arising:

- **The backend's mixed-direction sort is a trap for the next consumer.** Any caller that
  trusts API order — reasonably, since the endpoint bothers to sort — gets Autumn of the
  newest year. The correctness of the current behaviour rests entirely on one component
  choosing to re-sort.
- **The fallback should probably be "most recent term that has started", not "newest term
  that exists".** That is a product decision, not an audit finding, and it belongs with the
  M3 term-state work that deletes these derivations anyway.

Report only, per instruction. Nothing changed.

## Follow-up 2 — REQ-007, settled

The instruction was that the backend audit settles whether the `due_date` defect is backend
persistence or the by-aspect transform. **It settles it: the transform.**

- **Backend persists it.** `main.py:1009-1021` — `due_date` is in the INSERT column list and
  is bound from the request payload.
- **Backend returns it.** `main.py:3134` selects `a.due_date` in the by-aspect standards
  query; `main.py:3180` serialises it per standard as `YYYY-MM-DD` or `null`.
- **The frontend transform discards it.**
  `transformAssessmentByAspectToAssessment` (`use-assessments.ts:84`) builds the aggregate
  `Assessment` with **`due_date: null` hardcoded** (line 104), despite every entry in
  `data.standards[]` carrying a real value.

Knock-on: `isOverdue` returns `false` whenever `due_date` is null, so this transform also
suppresses overdue rendering wherever the aggregate is used. The list endpoint already solves
the same aggregation problem with `MAX(a.due_date)`; deriving it the same way in the
transform is the obvious fix shape.

Also settled, since REQ-007's backend scope asks: **no migration is needed.**
`assessments.due_date` (`date NULL`) already exists — data model §15, line 438.

Not fixed. REQ-007 scope.
