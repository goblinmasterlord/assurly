## Which surfaces changed, and which did not

Established before implementing, as instructed. **Three candidates, two changed.**

| Surface | Before | Decision |
|---|---|---|
| `GET /api/assessments/by-aspect/{aspect_code}` | returns neither `updated_by` nor a name | **Changed** — per standard **and** at the aspect level |
| `GET /api/assessments/{assessment_id}` | raw `updated_by`, no name | **Changed** — name join added |
| `GET /api/assessments` (grouped) | no `updated_by` in any form | **Not changed** — see below |

**by-aspect is the surface the report came from**, and that took tracing rather than guessing.
`AssessmentDetail.tsx` renders "Updated by" twice — the summary card (`:1756`) and the
per-standard table (`:1920`) — and **both are fed by by-aspect**, via
`transformAssessmentByAspectToAssessment` (`use-assessments.ts:86`). The single-detail endpoint
feeds neither, but it is the same defect in the same family and the join is one line.

**The grouped list is deliberately untouched.** It exposes no `updated_by`, no surface reads one
from it, and **a group-level "last editor" is not a missing join — it is an aggregate that has to
be designed**: the user behind `MAX(last_updated)` across the group, which needs a correlated
subquery or a window function. **Adding a capability nobody asked for, inside a defect fix, is
how scope leaks.** Recorded here so the next reader knows it was considered.

## The null case: an em dash, and one option turned out to be impossible

**Decision: `updated_by_name` is null when nobody has edited, and the client renders `—`. No
fallback.**

`updated_by` is written only on `UPDATE`, never on `INSERT`, so **null means "not yet edited" —
a fact, not a gap to be filled.** The two alternatives both answer a different question: the
assignee is who was *asked* to do it, the submitter is who *finished* it. Under a label reading
"Updated by", either is an assertion about authorship that is not true. **That is REQ-011's
lesson exactly** — it removed `|| new Date()` for the same reason — and it is the whole point of
REQ-047, since the fallback to the assignee *is* the defect.

**`submitted_by` was ruled out on evidence, not taste.** Both write paths — `main.py:3473` and
`:3551` — set `submitted_by` and `updated_by` **in the same `UPDATE` statement**. So any row with
a submitter has an updater, and **a row with no updater has no submitter either.** The rung is
**unreachable**, not merely undesirable. Worth stating because "fall back to the submitter" is
the reasonable-sounding option, and it would have been dead code.

**The 1142-of-1198 figure argues for the em dash, not against it.** If most rows are unedited,
then most rows currently name someone who did not edit them. **The scale of the null case is the
scale of the defect.**

**Recorded in the contract under Conventions**, because REQ-035 reuses it rather than deciding
again.

## What changed

**Backend:** `updated_by` + `u_updated.full_name as updated_by_name` on by-aspect's standards
query and on the single detail; a `LEFT JOIN users u_updated` on each. The **aspect-level** value
is derived in Python from the rows already fetched — the standard with the latest `last_updated`
that has an editor — rather than a second query.

**Frontend:** `AssessmentByAspect` gains the two fields; the transform carries them through
instead of leaving them undefined; **both display sites lost their fallback chains** and now read
`updated_by_name || "—"`.

**Schema changes: none.** The column, the FK and the write path all already existed.

## What was deliberately not changed

- **The grouped list.** See above.
- **`Standard`'s type.** The per-standard table still casts, because `Standard` does not declare
  `updated_by_name` and the hook attaches it via an intersection type. Widening a type used
  across the app is not this requirement's business.
- **`transformAssessmentByAspectToAssessment`'s other hardcoded nulls** — `due_date`,
  `assigned_to_name`, `submitted_by_name`, and `last_updated: || new Date().toISOString()`. See
  Findings; **one of them is REQ-007's frontend half and another is a live REQ-011 regression.**

## Findings — flagged, not fixed

- **🔴 The same transform fabricates a timestamp.** `use-assessments.ts:112` ends
  `|| new Date().toISOString()` — **the exact fabrication REQ-011 removed from the standards card
  and REQ-031 exists to remove from `VersionHistoryModal`.** An aspect whose standards have no
  `last_updated` reports **now**. This is a third instance of one defect, on a surface neither
  requirement names.
- **The same transform hardcodes `due_date: null`**, which is REQ-007's frontend half — the
  backend now computes an effective date and this line discards it.
- **Four rungs became one, and the chain was hiding the missing field.** A visible gap would have
  been reported in the first week; the fallback turned an API defect into a display nobody could
  tell was wrong. **That is REQ-048's argument, and this is its worked example.**
- **`GET /api/assessments`'s `last_updated` has the same asymmetry** — `MAX(a.last_updated)` with
  no updater. If a group-level editor is ever wanted, those two belong together.

## Verification

**Run against a real database** — the local MariaDB 10.11 fixture from the REQ-007/REQ-009
session, with synthetic rows. No production data or access (§2.4). The **actual handlers** were
exercised through `TestClient`.

The fixture was built so the display could fail: **the assignee (Ada) is not the last editor
(Ben)**, and one aspect has no edits at all.

| Case | Result |
|---|---|
| Standard edited by Ben, assigned to Ada | `updated_by_name: "Ben Reviewer"`, `assigned_to_name: "Ada Editor"` — **distinguished** |
| Aspect level, two edits at different times | **"Ben Reviewer"** — the *most recent* editor, not the earlier one |
| Aspect with no edits | `updated_by_name: null` at both levels |
| Standard with no assessment row | `updated_by_name: null` |
| Single detail, edited | `"Ben Reviewer"` |
| Single detail, never edited | `null`, while `assigned_to_name` is still "Ada Editor" |

- **`npx tsc -b` exit 0.**
- **Lint errors went down, and this was measured rather than assumed:** 33 → 30 on the three
  changed files, compared against a stashed tree. Removing the two IIFEs removed three
  `no-explicit-any` errors. **No new errors or warnings.**
- App boots: **47 routes, 43 operations / 31 paths** — unchanged, as expected for a field
  addition.
- **Not verified:** production, including how many rows actually carry an updater today.

## Notes for the release summary

*"Updated by" now names the person who last changed a rating. Previously it showed whoever the
assessment was assigned to, which was wrong whenever somebody else made the change. Where nobody
has edited an assessment yet, it shows a dash rather than a name.*
