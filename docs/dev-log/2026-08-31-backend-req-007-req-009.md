## ⚠️ `?status=` was returning 500 for every value, not 200 with an empty array

**The brief's symptom was that `?status=overdue` returns `200` and an empty array, so a caller
cannot tell a working filter from a broken one. It does not. It returns `500`, and so does every
other value.**

The filtered path wraps the grouped query in a derived table and then appends
`ORDER BY academic_year DESC, unique_term_id DESC, school_name`. **`unique_term_id` is not in the
inner `SELECT` list**, so it is not a column of the derived table:

```
ERROR 1054 (42S22): Unknown column 'unique_term_id' in 'ORDER BY'
```

Caught by the handler's bare `except Exception` and returned as `500`. **Executed against a
database to confirm it, not inferred** — see Verification.

**So the status filter has never worked for any value.** That is a larger defect than the one
reported, and it means adding `overdue` alone would have fixed nothing.

**Why nobody noticed:** **no frontend caller sends `?status=`.** The Assessments view filters
client-side (`utils/assessment.ts`, `SchoolPerformanceView.tsx`). **A defect in a parameter
nothing calls is invisible** — the same explanation as `/api/aspects/inactive` under REQ-012.

**The fix removes the divergence rather than patching it.** Both paths now share one shape —
always wrap, always order on the derived table — and order on `term_id`, which is a column of
`grouped` and sorts identically to `unique_term_id` with `academic_year` as the outer key. **The
bug existed because the two paths ordered differently; one shape is what stops it recurring.**

## Decisions worth the next reader's time

**`due_date` still reports the latest effective date; overdue is keyed on the earliest
outstanding one.** These are deliberately different aggregates: `due_date` answers "when must
everything be done", overdue answers "when did this first fall behind". **A group can therefore
read `overdue` while showing a future `due_date`.** That is correct and it reads oddly, so it is
documented in §21 rather than left for a client to discover. **I did not change `due_date` to
`MIN`** — the brief scoped the aggregate change to the overdue determination, and the field's
"latest across standards" meaning is documented and coherent on its own.

**`overdue` is tested first and a completed group is never overdue.** The three original branches
keep their original order beneath it, so **no existing outcome changes except those that become
overdue.** The `COUNT(completed) < COUNT(*)` guard is redundant — `MIN` over no outstanding rows
is `NULL`, and `NULL < CURDATE()` is not true — but it states the rule instead of leaving a
future reader to reconstruct it from NULL propagation.

**by-aspect joins `terms` on the requested term, not on `a.unique_term_id`.** Assessments are
`LEFT JOIN`ed there, so a standard with no assessment row has no term to inherit from — but the
request names the term, and that standard is being shown *as part of it*. **Verified: a standard
with no assessment row returns the term's end date rather than `null`.**

**The grouped `ORDER BY` had to be qualified in the REQ-007 commit.** The terms join introduces
its own `academic_year` and `unique_term_id`; without qualification the unfiltered path would
have started failing too. **That is the join forcing the change, not tidying.**

## What was deliberately not changed

- **Term-state awareness.** Overdue is computed against the calendar, so **a closed term's
  assessments keep reading as overdue.** REQ-015 introduces term state; recorded in the contract
  as a known limit rather than half-built.
- **`?status=` validation.** An unrecognised value still returns `200` and an empty array.
  Fixing it is out of the brief; recorded as **Known Issue #14**.
- **`transformAssessmentByAspectToAssessment`**, which nulls `due_date` on read. Frontend half.
- **`'approved'`.** The overdue test treats "done" as `status = 'completed'`, mirroring the
  group-completed branch exactly rather than introducing a second definition. See Findings.

## Findings — flagged, not fixed

- **`'approved'` is in the `assessments.status` enum and no branch of this `CASE` treats it as
  done.** An all-approved group reports `in_progress` today and will now report `overdue` once
  past due. **I mirrored the existing definition rather than inventing a second one**, but the
  enum value exists and the code does not believe in it. Worth settling in M3 with REQ-014.
- **The status filter is applied *after* grouping, so it cannot use an index** and the derived
  table is materialised in full before filtering. Irrelevant at 1,198 rows; worth knowing before
  this endpoint is asked to paginate (REQ-032).
- **`?status=` has no caller, and that is the second time an uncalled surface has hidden a
  defect.** REQ-012's `/api/aspects/inactive` was the first. **The pattern is worth a rule of
  thumb rather than a requirement: a documented parameter nothing exercises is not evidence of
  anything.**
- **The handler's bare `except Exception` turned a SQL error into `500 str(e)`** and leaked the
  column name to the client. Consistent with the rest of the file; related to REQ-046.

## What the next session needs to know

- **The frontend half of REQ-007 is still outstanding** — `transformAssessmentByAspectToAssessment`
  nulls the field the backend now computes correctly.
- **The gate must exercise `?status=` on all four values.** It returned `500` before this change
  for every one of them, and no automated test covers it.
- **`overdue` now shadows `not_started` and `in_progress`** for past-due groups. A client
  filtering on those two will see fewer rows than before. **That is intended**, and it is the
  most likely surprise at gate time.

## Verification

**Run against a real MySQL-compatible database, not reasoned about.** A throwaway **MariaDB
10.11** was installed locally and loaded with a synthetic schema and four groups. **No production
data and no production access — §2.4 stands; this is a test fixture, not the platform's
database.**

The **actual handlers** were exercised through `TestClient` with `get_db_connection` pointed at
that instance, so the queries under test are the ones in `main.py`, including parameter binding
and date serialisation.

| Group | Setup | Result |
|---|---|---|
| EDU / T1-2526 | Past term, no explicit dates, unrated | `due_date` **2025-12-31 inherited**, status **overdue** |
| EDU / T3-2627 | Future term; one unrated standard explicitly due 2026-01-15 | **overdue** — `MAX` would have said 2027-08-31 and reported `in_progress`. **This is the aggregate defect, demonstrated** |
| FIN / T3-2627 | Future term, no explicit dates, unrated | **not_started** — inheritance does not make future work overdue |
| GOV / T1-2526 | Past term, fully completed | **completed**, not overdue |

- `?status=` — **`overdue`, `not_started`, `completed`, `in_progress` all return `200`** and each
  returns exactly the right groups. **Before the change all four returned `500`**, confirmed on
  the same fixture.
- **Detail endpoint:** no explicit date → term end date; explicit date → **overrides**.
- **by-aspect:** every standard inherits the term end date, **including one with no assessment
  row**; the standard with an explicit date keeps it.
- `MAX` versus earliest-outstanding compared side by side on the same group: `overdue_by_MAX = 0`,
  `overdue_by_earliest = 1`.
- App boots: **47 routes, 43 operations / 31 paths** — unchanged, as expected for a
  query-only change.
- **Not verified:** anything in production, and the 180-of-180 create-path figure, which is taken
  as reported.
