## Root cause

**REQ-012.** Starlette matches routes in registration order, first match wins.
`/api/aspects/inactive` was captured by `/api/aspects/{mat_aspect_id}` with
`mat_aspect_id="inactive"`, which found no such row and raised the handler's own `404`. The
inactive handlers were unreachable dead code. Both handlers were otherwise correct — nothing
in them needed changing.

**REQ-010.** Three steps, only the first of which is a design fault. `mat_aspect_id` is minted
as `f"{current_mat_id}-{aspect_code_upper}"` from a field validated only for length, so the
primary key inherits whatever the user typed. It is then interpolated into a URL path
unencoded. The browser's URL parser rewrites `\` to `/` in a special scheme, the path gains a
segment, no route matches, and FastAPI returns `404` on a row that exists.

## Assumptions made

- **Version bumps recorded as 1.43.1 and 1.43.2.** §2.6 prescribes a patch bump per shipped
  requirement. Both are *code complete* but neither is deployed, and REQ-010 additionally has
  an unapplied migration. **If a bump means "in production" rather than "merged", these
  numbers are premature** — say so and I will correct the entry. This is the first
  requirement to ship in the programme, so the convention has not been exercised before.
- **The Starlette/uvicorn request-path behaviour underpinning both the fix and the migration's
  "hygiene not fix" framing is established by reasoning, not execution** — specifically that
  uvicorn percent-decodes the raw path before Starlette matches, so `%5C` becomes a literal
  backslash that `[^/]+` accepts, while `%2F` becomes `/` and still misses. I could not run
  the app. **Treat the claim that encoding alone repairs the existing broken rows as
  provisional until someone exercises it against a deployed revision** (§2.2.7).

## Findings — flagged, not fixed

- **The REQ-010 migration is not what unblocks the reported symptom, contrary to the plan's
  premise.** The plan records that "rows already minted with unescaped characters stay broken
  otherwise, and those rows are the reported symptom". On analysis that is wrong: the call-site
  encoding repairs them, because the database genuinely contains those characters and
  percent-encoding transmits them faithfully. The single exception is an id containing a
  literal `/`, which `%2F` cannot rescue. Discovery query 1b in the migration file settles
  whether any such row exists. **The migration is still worth applying** — it aligns the data
  with the new rule and stops correctness depending on every future call site remembering to
  encode — but it is schedulable, not blocking.
- **`delete_aspect` has a latent 500.** It archive-renames a custom aspect's primary key to
  `{id}-deleted-{ts}` after guarding on **active** standards only (409 if any exist). But
  `fk_mat_standards_aspect` is `ON UPDATE NO ACTION`, so an aspect with zero active and one or
  more **inactive** standards will fail the rename on the foreign key and surface as a generic
  `500` from the catch-all handler. Same class as REQ-010's migration problem — a PK rewrite
  under a non-cascading FK. Also recorded in §5 of the migration file.
- **`users-service.ts:55`** — the one remaining unencoded path interpolation in the codebase.
- **The `aspect_code` constraint is a contract-visible behaviour change.** `POST /api/aspects`
  will now return `422` for inputs it previously accepted. Contract §"Create Aspect" does not
  document the constraint. Not amended — out of scope for a defect fix, but it should be.

## `IT & Data` — investigated, still open

**The diagnosis does not explain it, and I have not stretched it to.**

Tracing the request path, both characters survive an unencoded round trip: the space is
percent-encoded to `%20` by the URL parser, `&` is a legal sub-delimiter in a path segment and
passes through untouched, uvicorn unquotes both, and Starlette's `[^/]+` matches the result.
The parameterised lookup then compares the exact string. `/api/aspects/HLT-IT & DATA` should
therefore succeed where `HLT-IT\DATA` fails, which is precisely what the report says does not
happen.

Ruled out: `vercel.json` (its only rewrite is the SPA catch-all and does not touch `/api` —
the frontend calls the Cloud Run origin directly); and client-side id reconstruction
(`CreateAspectModal.onSubmit` passes `aspect?.mat_aspect_id` through verbatim, so the id sent
is exactly what the API returned, despite the form uppercasing and lowercasing `aspect_code`
around it).

**Leading hypothesis — `is_active = 0`.** `update_aspect`'s existence check is
`WHERE mat_aspect_id = %s AND mat_id = %s AND is_active = 1`. A deactivated aspect returns the
same `404` for any name, entirely independently of characters. It is the handler's only other
404 branch.

**Second hypothesis — the code is clean and the name is not.** If "IT & Data" is a *renamed
default* aspect, its `aspect_code` is still `IT` and its id is `HLT-IT` — no special
characters anywhere, and the character diagnosis cannot apply by construction.

**One query distinguishes all of it:**

```sql
SELECT mat_aspect_id, aspect_code, aspect_name, is_active, source_aspect_id
FROM mat_aspects
WHERE aspect_name LIKE '%IT%Data%';
```

A clean `mat_aspect_id` with `is_active = 0` confirms the first hypothesis; a clean id with
`is_active = 1` means the 404 has a cause not yet identified and needs a fresh reproduction
with the network tab open.
