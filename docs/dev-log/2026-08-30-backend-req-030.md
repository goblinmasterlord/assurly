## The reported diagnosis is right about the symptom and wrong about the mechanism

The plan calls this **"the third literal-after-parameterised shadowing in `main.py`"**. It is not
one, and the distinction has a consequence.

**Starlette prefers a full match anywhere in the route table over an earlier partial match.** A
route whose path matches but whose method does not yields `Match.PARTIAL`; the loop keeps
looking, and only falls back to the partial — a `405` — if no full match exists anywhere.
**Verified by running it, not by reading it:**

| Setup | Result |
|---|---|
| `POST /x/reorder` registered **after** `GET /x/{id}` | **`200` — the POST wins** |
| No `POST` route at all, `GET /x/{id}` present | **`405`** |
| `GET /x/reorder` with `GET /x/{id}` above it | matched the parameterised route, `id="reorder"` |

**So the `405` was never an ordering fault. It is what a missing endpoint looks like when a
parameterised sibling is there to absorb the path** — the parameterised route converts a `404`
into a `405` and nothing more. REQ-012's two `/inactive` routes *were* genuinely shadowed,
because those are `GET`s colliding with a `GET`. This is the same family — a parameterised route
swallowing a literal path — but a different failure.

**Registered above the parameterised sibling anyway**, and the reason is in a comment at the
site: not to make this endpoint reachable, but because **the third row of that table is real**.
The day someone adds a `GET /api/standards/reorder`, ordering starts mattering, and having the
literal already in the right place is free.

**Consequence for REQ-013's planned route-ordering test — worth reading before it is written.**
That test would **not** have caught this defect: there was no route to be out of order. It would
also flag a correctly-working `POST` registered below a parameterised `GET` as a failure. It is
still worth having for the `GET`-on-`GET` case REQ-012 fixed, but **it should assert on same-method
collisions**, or it will produce false positives and miss the case that actually shipped.

## ⚠️ `autocommit=True`, so every `rollback()` in this file is a no-op

`DB_CONFIG` sets **`autocommit: True`** (`main.py:231`). Under autocommit each statement commits
as it executes, so `connection.commit()` is redundant and **`connection.rollback()` rolls back
nothing.** `main.py` has **18 `commit()` calls and 9 `rollback()` calls, and not one `begin()`.**

For this endpoint that is the whole requirement: "apply them in one transaction" is unachievable
by writing `commit()` at the end, which is what every neighbouring handler does. **The endpoint
calls `connection.begin()` explicitly** — pymysql issues a literal `BEGIN`, which opens a
transaction regardless of the autocommit setting — and only then writes.

**The nine other handlers are not fixed here.** See Findings; several of them do multi-statement
writes whose failure path assumes a rollback that does not happen.

## Reported before implementing, as asked

**`MatStandardUpdate.sort_order`: removing it is still right, and the case is stronger than the
plan recorded.**

- **The model is not merely ignoring the field — the model is entirely unused.** `MatStandardUpdate`
  is declared at `main.py:349` and **referenced nowhere.** `update_standard` takes
  `update_data: dict` and reads four keys by name; `sort_order` is not one of them. So the field
  was not "declared and ignored by the handler" so much as **declared on a model no route binds**.
- **Confirmed against the spec rather than assumed:** `MatStandardUpdate` does **not appear in
  `components.schemas`** at all, because FastAPI only emits models a route references. **So the
  removal changes nothing on the wire**, which is exactly what plan v2.10 predicted when it said
  no contract change was needed — for a slightly different reason than the one recorded.
- **Nothing else wanted the field.** The frontend sends `sort_order` only to
  `/api/standards/reorder` (`assessment-service.ts:295`), never to the `PUT`.

**Only the field was removed, not the model** — the model is dead code, but that is a separate
cleanup and REQ-030 is not a licence to do it. Flagged below.

## What was deliberately not changed

- **`MatStandardUpdate` itself.** Dead, and out of scope. Removing an unused model is a
  standalone tidy, not part of building an endpoint.
- **The nine handlers whose rollbacks do nothing.** Naming a systemic problem inside a
  single-endpoint requirement is right; fixing it there is not.
- **The `PUT` handler's `update_data: dict` signature.** Untyped request bodies are a real
  weakness — no validation, no spec — but changing it would alter the `PUT`'s accepted shape.
- **`updated_at = NOW()` in `update_standard`.** Correct there: a rename *is* a material edit.

## Findings — flagged, not fixed

- **`autocommit=True` makes error handling across `main.py` decorative.** Nine `except` blocks
  call `rollback()` and none can work. **The dangerous ones are the multi-statement handlers** —
  `update_standard` writes `standard_versions`, `mat_standards` and `standard_edit_log` in
  sequence, and a failure at the third leaves the first two committed, with a version row whose
  edit is unlogged. This is a defect class, not a defect, and belongs to whichever requirement is
  willing to take the whole file. **Related to the v2.14 lesson but not the same:** there the
  statement succeeded against nothing; here the statement succeeds and the *undo* does nothing.
- **`MatStandardUpdate` is dead code**, as is any assumption that the `PUT` validates its body.
  `update_standard` accepts an arbitrary dict, so a typo in a field name is accepted silently and
  changes nothing — the same silent-ignore shape REQ-030 exists to remove.
- **The reorder endpoint applies what it is given and infers nothing.** If a client sends a
  partial list, the omitted standards keep their old values and may now collide. **That is the
  right contract** — the alternative is guessing — but it means the frontend must send the full
  set for the aspect. Stated in §16a.
- **`sort_order` is `int NULL DEFAULT 0`** and nothing enforces uniqueness within an aspect. Ties
  fall back to whatever MySQL returns. Not introduced by this change; visible now that ordering
  is writable.

## What the next session needs to know

- **The frontend half is verification only** — per plan v2.11, it already surfaces failures with
  an error toast, so the gate needs the success path exercised: drag, drop, reload, confirm the
  order held.
- **The gate should also confirm `updated_at` did not move** on a reordered standard. That is
  the half of this change nothing else would notice, and it silently undoes REQ-011 if wrong.
- **Do not "fix" the route ordering back.** The comment at the site explains why it is where it
  is; without it, a future reader may reasonably conclude the placement is cargo cult.

## Verification

- **Exercised through the HTTP layer with a stubbed connection**, asserting on the statements
  actually issued rather than on the handler reading correctly:

  | Case | Result |
  |---|---|
  | Valid set | `200`; call order **`SELECT → BEGIN → executemany → COMMIT`** |
  | The write | contains **`updated_at = updated_at`** and **`mat_id = %s`**; params carry the MAT |
  | One id in another MAT | `404`, and **no `BEGIN`, no write, no `COMMIT`** |
  | Empty array | `400` |
  | Same id twice | `400` |
  | Non-integer `sort_order` | `422` |
  | Validation `SELECT` | scoped `AND mat_id = %s` |

- **Route ordering asserted from the live route table**, not from the source: `/api/standards/reorder`
  is registered between `/api/standards/inactive` and `/api/standards/{mat_standard_id}`.
- **App boots under the pinned stack:** 47 routes (was 46), **43 operations / 31 paths** (was
  42/30) — exactly one endpoint added. `StandardReorderRequest` present in the spec;
  `MatStandardUpdate` absent before and after.
- **The Starlette matching claim was tested, not asserted** — three cases in the table above,
  because "registered below and therefore unreachable" is precisely the kind of plausible
  mechanism §2.2's preamble warns about, and it happens to be false.
- **Not executed against a database.** No access — §2.4. **`updated_at = updated_at` suppressing
  `ON UPDATE CURRENT_TIMESTAMP` is MySQL-documented behaviour and is the one claim here that
  production has to confirm.**
