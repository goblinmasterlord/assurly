## What this session was for

Fix the indefinite loading spinner when a JWT expires. The backend returns a correct 401;
the client interceptor never completed the failure path, so queued requests and hook `finally`
blocks never ran.

## What changed

**REQ-042 (`api-client.ts`, `Login.tsx`):**
- Added `handleSessionExpired()` — rejects the failed queue, resets `isRefreshing`, clears
  the JWT via `authService.clearSession()` (localStorage `assurly_auth_token`), redirects to
  `/auth/login?reason=session_expired`.
- Treat `refreshSession()` returning `null` the same as a throw. Previously execution left
  the `try` when `if (response)` was false, leaving `isRefreshing === true` and
  `failedQueue` unsettled.
- Login page reads `reason=session_expired` and shows a destructive toast explaining the
  session expired.
- Removed the old redirect path that cleared `sessionStorage['assurly_secure']` only — wrong
  store for the JWT.

**Schema changes:** none.

**Contract changes:** none.

## What was deliberately not changed

- **`authService.refreshSession()` stub** (`auth-service.ts:153`) — left in place; backend
  half of REQ-042 will give it a real `/api/auth/refresh` endpoint. Frontend no longer
  depends on it succeeding; null is handled as failure.
- **Backend** — out of scope; diagnostic in `docs/dev-log/2026-08-30-backend-req-042-part1.md`.
- **`get_current_user` 401→500 loop for deactivated users** — REQ-013; flagged in backend
  REQ-042 report, not fixed here.

## Root cause

On 401, the interceptor awaited `refreshSession()`. That stub calls `getCurrentSession()`,
which catches its own 401 and returns `null` rather than throwing. The interceptor only
handled failure in `catch`, so `isRefreshing` stayed true and every subsequent 401 was pushed
onto `failedQueue` with promises nobody settled. `use-assessments.ts` set `isLoading(true)`
and never reached `finally` — the spinner.

The redirect-to-login code in the old `catch` block was unreachable on this path. Token
clearing targeted `sessionStorage['assurly_secure']` while the token lives in
`localStorage['assurly_auth_token']`.

## Assumptions made

- Full-page redirect to login is acceptable for session expiry (matches existing catch-path
  behaviour).
- Calling `refreshSession()` before failing is still worth keeping so the backend half can
  plug in without another interceptor change.
- `/api/auth/*` paths remain excluded from the refresh branch (prevents recursion on `/me` 401).
