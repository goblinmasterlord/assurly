## What this session was for

Three related frontend defects in `transformAssessmentByAspectToAssessment` and its consumers: fabricated last-updated timestamps (REQ-050, absorbing REQ-031), discarded effective due dates and an unclickable invitation date picker (REQ-007 frontend half), and a case-sensitive category map (REQ-049).

## What changed

- `assurly-frontend/src/hooks/use-assessments.ts` — removed `|| new Date().toISOString()` from `last_updated` / `lastUpdated`; derive `due_date` / `dueDate` as the latest effective date across standards instead of hardcoding null.
- `assurly-frontend/src/components/admin/standards/VersionHistoryModal.tsx` — show em dash when no `updated_at` or `created_at`; no fabricated date.
- `assurly-frontend/src/pages/AssessmentDetail.tsx` — em dash for absent last updated; due date reads `due_date || dueDate`.
- `assurly-frontend/src/types/assessment.ts` — `last_updated` and `lastUpdated` typed as nullable.
- `assurly-frontend/src/components/AssessmentInvitationSheet.tsx` — `modal={false}` on Popover and `z-[100]` on PopoverContent.
- `assurly-frontend/src/lib/data-transformers.ts` — `aspectCodeToCategory` uses `aspectCode.toUpperCase()` before map lookup.
- `assurly-frontend/src/lib/v4-adapter.ts` — `LegacyAssessment.lastUpdated` aligned to `string | null` (compile fallout from nullable type; module is unused).

**Schema changes:** none

**Contract changes:** none

## What was deliberately not changed

- **`v4-adapter.ts` fabrication (`lastUpdated: new Date().toISOString()` at line 103).** The module has no importers; fixing it would be dead-code churn. Flagged in Findings.
- **`getCategoryIcon` in `Assessments.tsx`.** REQ-049 scope was the map lookup only. Unmapped custom codes (`ld`, `ab`, `ey`, `mck`) may still warn — see Findings.
- **`transformAssessmentByAspectToAssessment` sets `category: data.aspect_code.toLowerCase()`** rather than calling `aspectCodeToCategory`. Out of REQ-049 scope; separate from the map defect.
- **`enhanced-assessment-service.ts` optimistic `last_updated: new Date().toISOString()`.** Write-path optimistic UI, not a display fabrication; out of REQ-050 scope.

## Root cause

**REQ-050:** Display paths used `|| new Date()` as a silent default when `last_updated` was absent. The majority of assessments have never been edited, so the fabricated timestamp read as real data.

**REQ-007 (due date):** `transformAssessmentByAspectToAssessment` hardcoded `due_date: null` after the backend began returning `COALESCE(a.due_date, t.end_date)` on every read path (contract v2.12). The detail header already had a Due Date card but read only the camelCase field the transform left undefined.

**REQ-007 (date picker):** Confirmed Popover-in-Sheet stacking. Both Sheet overlay and Popover content use `z-50`; the portaled Popover rendered at the same stacking level as the full-screen Sheet overlay, so pointer events hit the overlay while keyboard focus could still reach the calendar. `modal={false}` plus `z-[100]` on PopoverContent resolves it without changing the Sheet.

**REQ-049:** `aspectCodeToCategory` keyed the map with the raw `aspect_code`. Stored lowercase codes (`edu`, etc.) missed the uppercase map and fell through to `aspectCode.toLowerCase()`, diverging from assessments returned with API-uppercased codes on `GET /api/assessments`.

## Assumptions made

- Aspect-level due date on the detail page is correctly derived as the **latest** effective date across standards, matching §21's group aggregate. The by-aspect API exposes `due_date` per standard only; no aspect-level field exists in the contract.
- The Popover z-index fix is sufficient in production; not browser-verified in this session (no running dev server with auth).

## Findings — flagged, not fixed

- **`v4-adapter.ts:103`** still fabricates `lastUpdated: new Date().toISOString()` in `adaptAssessmentByAspectToLegacy`. No importers — safe to delete the module under DOC-002 or fix when touched.
- **`getCategoryIcon` warnings for unmapped codes** (`ld`, `ab`, `ey`, `mck`) will persist: those codes are not in `aspectCodeToCategory`'s map regardless of casing. Cosmetic only per plan §REQ-049 analysis; filter options and assessment categories still agree because both sides miss the map identically.
- **`use-assessments.ts:149`** sets `category: data.aspect_code.toLowerCase()` on the by-aspect transform, bypassing `aspectCodeToCategory` entirely. Aspect-detail routing uses raw codes as categories; inconsistent with the list path but pre-existing and out of scope.
- **`AssessmentDetail.tsx` mobile card still shows "No due date"** when both fields are absent. With effective due dates from the backend this should be rare; em dash was not applied here (only last updated was brought to REQ-047 convention in this session).
